# crowd-test · 300 人虚拟用户众测

模拟 300 名性格各异的虚拟用户，对**可真实访问**的产品进行体验测试，产出类应用商店综合评分、性格分群评分、结构化 Bug 清单与 Markdown 报告。

## 四条铁律

1. **300 用户必须真实生成**：运行 `scripts/generate_users.py` 产生全部 300 份画像，禁止口头宣称"已生成 300 人"却只靠想象。
2. **必须真实访问产品**：用浏览器实测或通读代码来发现问题，Bug 必须有真实依据；产品不可访问时向用户索要入口（URL / 本地路径），不要凭产品描述脑补。
3. **一切归属到具体用户**：每个评分、每个 Bug、每条原声都必须挂在某个真实用户 ID 上，且符合其性格。
4. **分阶段输出**：对话中只放摘要和样本，完整 300 条明细只进报告文件，避免刷屏。

## 工作流程

### 阶段一：确认产品与功能清单

1. 拿到产品入口：URL（用浏览器工具访问）或本地项目路径（读代码 + 可运行则运行）。二者都没有 → 向用户索要，**此时不要开始测试**。
2. 实测中梳理功能清单，为每个功能标注复杂度（简单/中等/复杂），列出并请用户确认范围（有无豁免功能、已知问题）。

### 阶段二：生成 300 名用户

```bash
python3 scripts/generate_users.py --seed <S> --out users.json
```

- seed 规则：**首次测试**用当天日期数字（如 20261001）并记录下来；**回归测试**必须复用首次的 seed，保证 300 人是同一批。
- 将脚本 stdout 的样本表（前 15 + 后 15）和统计摘要原样贴给用户，附一句"300 名用户已就绪，开始实测"。

### 阶段三：真实测试并记录发现

1. 逐个功能真实操作（浏览器点击、输入、边界值、异常输入、不同视口；或运行代码做接口/并发测试）。
2. 每个真实发现记录为 `findings.json` 中的一条 bug（格式见下），`reporter` 指定给**最可能发现它的用户**——先读 `references/personas.md` 查看 30 种性格的主攻 Bug 方向， attribution 要合理（如 XSS → 安全专家，像素偏差 → 完美主义者，且尽量用该性格中 bug_sensitivity 高的人）。
3. 基于真实体验定**客观质量基准分 base**（1.0–5.0），锚定标准：
   - 5 = 惊艳，几乎挑不出毛病；4 = 好用，有小瑕疵；3 = 及格，有明显短板；2 = 难用，核心体验受损；1 = 基本不可用。
4. 撰写 15–20 条**用户原声**（`quotes`）：正负面混合、口吻符合各性格（参考 personas.md 的口吻示例）、有画面感，像真实应用商店评论。每条引用真实存在的用户 ID。

`findings.json` 格式：

```json
{
  "bugs": [
    {"severity": "P0", "title": "一句话标题", "feature": "功能模块",
     "steps": "复现步骤", "expected": "预期行为", "actual": "实际行为",
     "suggestion": "修复建议", "reporter": "U095"}
  ],
  "quotes": [{"user": "U095", "text": "这个接口鉴权了吗？"}]
}
```

严重等级：P0 致命（崩溃/数据丢失/安全漏洞/核心功能不可用）｜P1 严重（核心功能部分不可用且无绕过）｜P2 一般（非核心异常，有绕过）｜P3 轻微（界面瑕疵/文案错误）｜P4 建议（优化项）。

### 阶段四：聚合与交付

```bash
python3 scripts/build_report.py --users users.json --findings findings.json \
    --base <B> --product "<产品名>" --seed <S> --out "众测报告-<产品名>.md"
```

- 评分由脚本按 `score = clamp(base + rating_bias×0.5 + 噪声, 1.0, 5.0)` 确定性计算，不要自己编分数。
- 对话中：贴脚本 stdout 的总览卡片 + 🔴 P0/P1 紧急清单，并用一段话总结"谁最满意/谁最不满、最值得修的 3 个问题"。
- 完整报告（含性格分群表、全部 Bug 详情、原声、300 人评分明细）以 Markdown 文件交付给用户。
- 结尾附："修复 P0/P1 后可再次运行 crowd-test 回归验证评分变化。"

### 阶段五：回归测试（用户修复后再次发起时）

1. 用**相同 seed** 重新运行 generate_users.py（同一批 300 人）。
2. 重新实测，写新 findings.json，重定 base。
3. build_report.py 增加 `--previous <上一轮的 summary.json>`（路径为上一轮报告同名 `.summary.json`），报告自动带回归对比。

## 用户体验规范

- 每个阶段开头用一句话播报进度（"正在实测第 3/6 个功能：搜索…"），不要长时间沉默。
- 对话中单个表格不超过 30 行；300 条评分明细只放报告文件。
- 不要重复打印脚本已输出过的内容；直接引用脚本 stdout。
- 用户只想要快速结论时（"大概测一下"），仍走完整流程，但功能清单确认和阶段播报从简。
